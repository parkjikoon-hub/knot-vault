## 2. 적용 방향 결론

StudyCapture에서 `Codex`를 가장 먼저 붙일 위치는:

`저장 직전 과목 추천 + 파일명 추천`

입니다.

이유:

1. 촬영 실시간 경로를 건드리지 않아도 됨
2. Drive 저장 로직을 크게 바꾸지 않아도 됨
3. 현재 수동 입력 구간이라 AI 보조 효과가 큼
4. PRD의 자동 분류 요구와 정확히 맞음

[산출근거: 현재 코드 구조와 PRD를 함께 검토한 결과, 저장 직전 추천 단계가 가장 작은 변경으로 가장 큰 사용자 체감 효과를 줄 수 있다고 판단함]

## 4. 최소 PoC 범위

처음에는 아래만 구현합니다.

- 추천 과목 1개
- 대안 과목 1개
- 추천 파일명 1개

처음부터 하지 않는 것:

- 실시간 자동 저장
- 완전 무인 자동 분류
- 실시간 카메라 분석
- Drive 업로드 경로 자동 변경

## 5. 추천 API 초안

### 엔드포인트

`POST /api/ai/suggest-capture`

### 입력 예시

```json
{
  "capturedAt": "2026-05-10T10:12:00+09:00",
  "ocrText": "삼각함수 기본 문제...",
  "subjects": ["수학", "영어", "국어"],
  "timetable": {
    "semester": "2026-1",
    "schedule": []
  }
}
```

### 출력 예시

```json
{
  "subject": "수학",
  "alternatives": ["국어"],
  "confidence": 0.93,
  "suggestedFileName": "2026-05-10-3교시-수학-삼각함수",
  "reason": "촬영 시각과 OCR 키워드가 수학 수업 시간과 가장 잘 맞음"
}
```

## 6. 구현 순서

### 1단계

추천 API 설계 및 서버 연결 지점 확인

### 2단계

저장 모달에 기본값 주입 구조 추가

### 3단계

추천 실패 시 기존 수동 입력 유지

### 4단계

타임아웃과 예외 처리

### 5단계

테스트:

- 시간표 없음
- OCR 없음
- OCR 있음
- 추천 실패
- 수동 수정 후 저장

## 9. 제 판단으로 추가하는 더 좋은 의견

### 9-1. 첫 PoC는 `Codex` 직접 연동보다 `추천 API 인터페이스`부터 먼저 고정하는 것이 좋습니다

즉, 처음에는 내부 구현을 완전히 `Codex`에 의존하지 않고, 아래처럼 만드십시오.

- 프론트엔드 → `suggest-capture` API 호출
- 그 API 안에서 나중에 `Codex`, 규칙 기반, 또는 혼합형으로 교체 가능

이렇게 해두면 추후 엔진 교체가 쉬워집니다.

[산출근거: 추천 API 인터페이스를 먼저 고정하면 백엔드 구현체를 교체해도 프론트엔드 변경을 최소화할 수 있다는 일반적 서비스 설계 원칙에 의거하여 제안함]

### 9-2. 첫 버전은 `Codex + 규칙 기반 혼합형`이 더 실용적일 수 있습니다

예:

- 시간표 매칭은 규칙 기반
- OCR 키워드 보강과 파일명 생성은 Codex

이 방식이 순수 AI 의존보다 더 안정적일 가능성이 큽니다.

[산출근거: 시간표-시간 매칭은 규칙성이 높고, OCR 후처리와 파일명 생성은 AI 강점이 있으므로 혼합형이 더 안정적이라고 추산함]

## 10. 한 줄 결론

StudyCapture에는 `Codex`를 촬영 엔진이 아니라 `저장 직전 추천 엔진`으로 붙이는 것이 가장 안전하고, 가장 작게 시작하면서도 가장 큰 사용자 체감 효과를 얻을 수 있는 첫 단계이다.
